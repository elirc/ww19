# Separate solutions and review rubric

Level 1 stops after lookup and returns the original row; changed payload is ignored under current semantics. Level 2 stores `u2:k`, so it creates independently. Level 3 stops after lookup/version with 404 and no parse or transaction. Level 4 propagates the seed error after `tx-done`, leaves one created run, and replay returns it without another seed. Level 5 yields 500 after reload, with exactly one create; a retry policy for reload is a separate design decision.

Review the implementation for correct user-scoped identity, exact create payload, parse-before-transaction ordering, explicit transaction completion before seed, and no duplicate create on replay. The five-case lab executes the real service and asserts these traces. It does not prove concurrent uniqueness, remote engine idempotency, or transaction rollback. Reject documentation that says idempotent without naming the key scope and replay behavior. Ask whether same-user different payload should return old data or conflict; current behavior returns old data. Ask how a unique violation during concurrent create maps to a replay. Keep those future choices separate from the verified workflow.
