# Concepts: identity, idempotency, and transaction scope

An idempotency key answers whether this is the same command retry. Here the key is scoped as `${user.id}:${input.idempotencyKey}`. Two users using `k` therefore create distinct rows. One user replaying `k` receives the old row even if the second request changes display name or input. That is intentional request identity, not payload equality. If product needs payload mismatch detection, it needs a stored request fingerprint and explicit conflict policy.

The transaction scope is equally important. The run row is created and committed before seed execution starts. This reduces transaction duration but it means the create and seed are not atomic. The lab demonstrates that seed failure leaves one row and replay returns it without a second seed. Missing active version and parse failure happen before the transaction, so they create nothing. Missing reload after seed is treated as 500 because the service cannot return its newly created resource. The [source](../src/services/workflow-run-service.ts) and [repository](../src/repositories/workflow-run-repository.ts) show the boundaries. Live uniqueness concurrency remains unverified.
