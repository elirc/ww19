# Worked flow

The useful before-and-after is a trace, not a production patch. Before reading the expanded lab, a learner might assume seed failure rolls back creation or that a changed replay payload updates the original run. The actual flow is: lookup scoped key, resolve active version, parse definition, transaction create, transaction completion, seed, reload. The create payload includes `workflowVersionId`, `startedById`, display name, scoped idempotency key, input, copied context, PENDING status, and initial step key.

For same-user replay, the flow stops after lookup and returns the original row. A different user gets a different scoped key and a new row. For seed failure, the transaction has already completed; the error propagates, but the persisted row remains. A retry stops at lookup and does not seed again. For missing reload, create and seed have occurred, then the service raises 500 without creating another row. See [workflow-run-idempotency.test.mjs](../tests/workflow-run-idempotency.test.mjs) and [workflow-run-service.ts](../src/services/workflow-run-service.ts). The adapter proves call ordering and payload shape, not live uniqueness races or engine durability.
